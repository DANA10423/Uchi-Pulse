# Uchi-Pulse CDC通信仕様書

## 1. 目的

本仕様書は、Uchi-PulseにおけるUSB CDC通信の共通仕様を定義する。

CDC通信は、親機および子機をPC等から直接管理するためのローカル管理・保守インターフェースとして使用する。

通常運用時の親機・子機間通信はWi-Fi/UDPを使用し、CDC通信はこれとは独立した管理用通信路とする。

## 2. 適用対象

本仕様は以下のターゲットに共通して適用する。

- 親機: Raspberry Pi Zero W / Zero 2 W（Linux）
- 子機: Raspberry Pi Pico W / Pico 2 W

親機と子機ではUSB CDCの低レベル実装が異なるが、CDC上で使用するプロトコル、メッセージ形式、コマンド体系、応答形式およびエラー体系は共通化する。

## 3. 基本方針

### 3.1 CDC通信の責務

CDC通信は以下の機能を提供する。

- ターゲット情報の取得
- 設定情報の取得
- 設定情報の変更および保存
- ターゲットの現在状態の取得
- 入力状態の取得
- 出力状態の取得
- ターゲットの再起動
- 保存設定の初期化
- 将来追加される保守・診断機能

### 3.2 CDC通信で扱わないもの

以下は本CDC通信仕様の責務外とする。

- 親機・子機間の通常イベント通信
- UDP EVENTのACKおよび再送制御
- ボタンへ割り当てるマクロ／アクションそのものの定義
- 各ターゲット固有機能の内部処理仕様

ボタン等に割り当てるマクロ／アクションは別仕様で定義し、CDCでは設定値として取得・変更する対象としてのみ扱う。

## 4. 共通クレート

CDC通信の共通部分はRustの共通クレートとして実装することを前提とする。

想定クレート名:

```text
uchi-pulse-cdc
```

共通クレートは少なくとも以下を担当する。

- プロトコルバージョン定義
- JSONメッセージ定義
- コマンド定義
- 応答定義
- エラー定義
- JSONエンコード／デコード
- メッセージ境界処理

親機と子機で異なる以下の処理は、共通クレートから分離する。

- USB CDCデバイス／OS依存I/O
- コマンドの実処理
- 設定保存先へのアクセス
- GPIO等のハードウェア操作
- Linux固有処理
- Pico/Embassy固有処理

概念構成:

```text
                    +------------------+
                    |  uchi-pulse-cdc  |
                    |------------------|
                    | Protocol         |
                    | Command          |
                    | Response         |
                    | Error            |
                    | JSON Codec       |
                    +---------+--------+
                              |
               +--------------+--------------+
               |                             |
        +------v------+               +------v------+
        | Hub / Linux |               | Node / Pico |
        | CDC I/O     |               | CDC I/O     |
        | Handler     |               | Handler     |
        +-------------+               +-------------+
```

子機で利用できるよう、共通クレートは可能な限り`no_std`で利用可能な構成を前提とする。Linux側では必要に応じて`std`機能を使用できるものとする。

## 5. 通信方式

### 5.1 物理／論理通信路

USB CDCを使用する。

PC等の管理側から見た通信路はシリアル通信として扱う。

### 5.2 データ形式

通信データはUTF-8 JSONとする。

### 5.3 メッセージ境界

1メッセージを1行とし、LF（`\n`）をメッセージ終端とする。

```text
{"version":1,"command":"get_status"}\n
```

受信側はデータを受信バッファへ蓄積し、LFを検出した時点で1メッセージとしてJSON解析を行う。

### 5.4 通信モデル

原則として要求・応答型とする。

```text
管理側                ターゲット
  |                       |
  |------ Request ------->|
  |                       |
  |<----- Response -------|
  |                       |
```

1つの要求に対して1つの応答を返す。

UDP EVENT通信で使用しているACK、message_idによる重複排除、ACKタイムアウト、再送制御はCDC通信では使用しない。

## 6. プロトコルバージョン

初期プロトコルバージョンを`1`とする。

すべての要求および応答に`version`を含める。

```json
{
  "version": 1
}
```

未対応のバージョンを受信した場合はエラー応答を返す。

## 7. 要求メッセージ

基本形式:

```json
{
  "version": 1,
  "command": "get_status"
}
```

コマンド固有のパラメータが必要な場合は、追加フィールドとして定義する。

## 8. 応答メッセージ

### 8.1 成功応答

```json
{
  "version": 1,
  "result": "ok",
  "data": {}
}
```

`data`の内容はコマンドごとに定義する。

データを必要としないコマンドでは`data`を省略可能とする。

### 8.2 エラー応答

```json
{
  "version": 1,
  "result": "error",
  "error": {
    "code": "INVALID_COMMAND",
    "message": "unsupported command"
  }
}
```

`code`はプログラムによる判定に使用し、`message`は人間が確認するための補助情報とする。

## 9. 共通コマンド

初期仕様では以下の共通コマンドを定義する。

| 分類 | command | 内容 |
|---|---|---|
| 情報 | `get_info` | ターゲット固有情報を取得する |
| 設定 | `get_config` | 保存されている設定情報を取得する |
| 設定 | `set_config` | 設定を変更し保存する |
| 状態 | `get_status` | 現在の稼働状態を取得する |
| 診断 | `get_inputs` | 現在の入力状態を取得する |
| 診断 | `get_outputs` | 現在の出力状態を取得する |
| 保守 | `reboot` | ターゲットを再起動する |
| 保守 | `factory_reset` | 保存設定を初期状態へ戻す |

親機・子機で同じコマンド名を使用する。

コマンドに対する具体的な処理および`data`の内容は、ターゲット固有仕様に従う。

## 10. コマンド概要

### 10.1 get_info

比較的静的なターゲット情報を取得する。

対象例:

- ターゲット種別（hub / node）
- ハードウェアモデル
- ファームウェア／ソフトウェアバージョン
- デバイス識別情報

設定値や現在の動作状態とは分離する。

### 10.2 get_config

現在保存されている設定情報を取得する。

「現在どのように設定されているか」を取得するコマンドであり、実際の接続状態等は`get_status`で取得する。

### 10.3 set_config

設定情報を変更する。

初期実装では、設定値の検証と永続保存を一つの操作として実行する。

設定変更は原則として次回起動時に反映する。

これにより、実行中のWi-Fi、GPIO、UDP等を動的に再構成する必要をなくす。

変更可能な設定項目および設定値の詳細は、親機／子機の設定仕様で別途定義する。

### 10.4 get_status

ターゲットの現在の動的状態を取得する。

対象例:

- 稼働時間
- ネットワーク接続状態
- IPアドレス
- 親機／子機通信状態
- その他ターゲット固有の稼働状態

`get_config`が設定値を返すのに対し、`get_status`は実際の現在状態を返す。

### 10.5 get_inputs

現在の入力状態を取得する。

具体的な入力種別やチャンネル定義はターゲット固有仕様で定義する。

### 10.6 get_outputs

現在の出力状態を取得する。

具体的な出力種別やチャンネル定義はターゲット固有仕様で定義する。

### 10.7 reboot

設定を保持したままターゲットを再起動する。

応答送信完了後に再起動を実行する。

### 10.8 factory_reset

永続保存されているユーザー設定を初期状態へ戻す。

誤操作防止のため、明示的な確認パラメータを要求する。

要求例:

```json
{
  "version": 1,
  "command": "factory_reset",
  "confirm": true
}
```

初期化対象の具体的な範囲は設定保存仕様で定義する。

原則として初期化完了応答を送信した後、ターゲットを再起動する。

## 11. エラー処理

初期仕様として以下のエラーコードを定義する。

| code | 内容 |
|---|---|
| `INVALID_JSON` | JSONとして解析できない |
| `UNSUPPORTED_VERSION` | 未対応プロトコルバージョン |
| `INVALID_COMMAND` | 未定義コマンド |
| `INVALID_PARAMETER` | パラメータが不正 |
| `INVALID_CONFIG` | 設定内容が不正 |
| `SAVE_FAILED` | 設定保存に失敗 |
| `OPERATION_FAILED` | コマンド処理に失敗 |
| `NOT_SUPPORTED` | 対象ターゲットでは機能をサポートしない |

ターゲット固有のエラーが必要になった場合は追加可能とする。

## 12. 設定情報の扱い

CDC通信は設定情報の転送と操作を担当するが、設定データそのものの詳細および永続化方式は別仕様とする。

基本的な設定処理は以下とする。

```text
set_config
    |
    v
設定値検証
    |
    v
永続保存
    |
    v
成功応答
    |
    v
次回起動時に反映
```

子機ではFlash等への永続保存が必要となる。

親機ではLinux上の永続ストレージを使用する。

保存媒体は異なるが、CDCから見た`get_config` / `set_config`インターフェースは共通とする。

## 13. ターゲット固有処理

共通CDCクレートはコマンドの意味と通信形式を定義するが、実際の処理は各ターゲット側のCommand Handlerが担当する。

```text
CDC Request
    |
    v
uchi-pulse-cdc
    |
    v
Command
    |
    +---------------------+
    |                     |
    v                     v
Hub Handler           Node Handler
(Linux)               (Pico)
```

ターゲットが特定コマンドを実装できない場合は`NOT_SUPPORTED`を返す。

## 14. 処理フロー

基本的な受信処理は以下とする。

```text
USB CDC受信
    |
    v
受信バッファ
    |
    v
LF検出
    |
    v
JSON解析
    |
    v
version検証
    |
    v
command解析
    |
    v
Command Handler
    |
    v
Response生成
    |
    v
JSONエンコード
    |
    v
LF付加
    |
    v
USB CDC送信
```

不正な要求についても、可能な限りエラー応答を返し、CDC通信処理自体は継続する。

## 15. 拡張方針

CDCプロトコルは将来の機能追加を考慮し、以下の方針で拡張する。

- 共通コマンドは親機・子機双方で意味を統一する。
- ターゲット固有機能は必要に応じて追加コマンドとして定義する。
- 未対応コマンドは`NOT_SUPPORTED`または`INVALID_COMMAND`で明確に応答する。
- 既存フィールドの意味を変更する破壊的変更はプロトコルバージョンを更新する。
- マクロ／アクションの具体的な定義はCDC仕様から分離する。
- USB/OS/MCU固有実装を共通プロトコル層へ持ち込まない。

## 16. 実装上の前提

本仕様に基づき、以下の構成で実装可能である。

1. `uchi-pulse-cdc`共通クレートを作成する。
2. 共通クレートにプロトコル、コマンド、応答、エラー、JSON codecを実装する。
3. 子機にPico用USB CDC I/OとCommand Handlerを実装する。
4. 親機にLinux USB Gadget CDC I/OとCommand Handlerを実装する。
5. 設定永続化層は親機・子機それぞれの環境に合わせて実装する。
6. CDC上の外部インターフェースは親機・子機で共通化する。

---

本仕様はCDC通信に限定する。ボタンへ割り当てるマクロ／アクション、各設定項目の詳細、設定保存形式およびターゲット固有機能については別途仕様化する。
