# 家庭内ゆるコミュニケーションツール プログラム設計書

## 1. 文書概要

### 1.1 目的
本システムは、家庭内で発生する簡単な連絡・状態共有・問い合わせを、スマートフォンのメッセージアプリ等に依存せず、物理ボタンを中心とした簡単な操作で行うための「家庭内ゆるコミュニケーションツール」である。

家族ごとに設置する子機からイベントを発生させ、家庭内LAN上の親機がイベント・状態・予定を一元管理する。家族はスマートフォンのWebブラウザから情報を確認でき、必要なイベントについては登録済みスマートフォンへの通知を行える構成とする。

### 1.2 基本方針
- 日常的な操作は物理ボタンを中心とする。
- 子機は Raspberry Pi Pico W または Raspberry Pi Pico 2 W を使用する。
- 親機は Raspberry Pi Zero W または Raspberry Pi Zero 2 W を使用する。
- 子機と親機は家庭内Wi-Fiを使用して通信する。
- 子機同士は原則として直接通信せず、親機を介して情報を交換する。
- 家族向けの情報表示・予定入力・履歴確認は親機のWeb UIから行う。
- 子機の設定にWeb UIは使用しない。
- 子機の初期設定・GPIO割り当て等はUSB CDC接続による有線設定を基本とする。
- 子機は共通ファームウェアを基本とし、端末ごとの差異は設定によって吸収する。

## 3. 構成機器

### 3.1 子機

対象ハードウェア：

- Raspberry Pi Pico W
- Raspberry Pi Pico 2 W

子機は家庭内イベントを発生・受信する汎用I/Oノードとして動作する。

### 3.2 親機

対象ハードウェア：

- Raspberry Pi Zero W
- Raspberry Pi Zero 2 W

親機はシステム全体の中央管理装置として動作する。

新規構築時には、処理能力に余裕のある Raspberry Pi Zero 2 W を基準構成として検討する。

### 3.3 スマートフォン

専用アプリを必須とせず、親機が提供するWeb UIをブラウザから利用する。

主な用途：

- 家族の現在状態確認
- 最近発生したイベントの確認
- 家族の大まかな予定確認
- 予定入力
- システム情報の閲覧
- 必要なイベント通知の受信

## 4. 子機設計

### 4.1 基本コンセプト

子機は「イベントボタンを必須装備した、Wi-Fi対応の汎用家庭内イベントI/Oノード」とする。

子機ごとに専用ファームウェアを作成するのではなく、可能な限り共通ファームウェアを使用する。

用途の違いは以下の設定によって吸収する。

- 端末識別情報
- 利用者情報
- GPIO割り当て
- 入力に対応するイベント機能
- 出力に対応する表示・通知機能

### 4.2 イベントボタン

家族用子機では、物理イベントボタンを必須構成とする。

イベント機能はあらかじめシステム側で複数種類を定義し、初期設定時に各ボタンへ割り当てる。

想定イベント例：

| イベント | 内容 |
|---|---|
| MEAL_READY | ご飯だよ |
| CALL | ちょっと来て／呼び出し |
| BUSY | 取り込み中 |
| BUSY_CLEAR | 取り込み中解除 |
| ENTRY_REQUEST | 入室してよいか問い合わせ |
| ENTRY_OK | 入室可 |
| ENTRY_LATER | 少し待って |
| ENTRY_NG | 入室不可 |
| MAIL_DETECTED | ポストへの投函検出 |
| MAIL_CLEARED | 郵便物回収済み |

イベント種類は今後の設計で追加可能とする。

### 4.3 GPIO入力

GPIO入力は物理ボタンだけに限定しない。

将来的に以下のような入力機器を接続できる構成とする。

- 押しボタン
- スイッチ
- ポスト投函検出センサー
- その他のデジタルセンサー

GPIO番号と家庭内イベントの意味を直接固定せず、論理入力を介してイベントへ変換する。

```text
GPIO入力
   ↓
論理INPUT
   ↓
イベント定義
   ↓
親機へ送信
```

例：

```text
GPIO 2 LOW検出
    ↓
INPUT_1 ACTIVE
    ↓
ENTRY_REQUEST
    ↓
親機へイベント送信
```

### 4.4 GPIO出力

GPIO出力は将来的な表示・通知機器接続のために使用する。

想定用途：

- LED
- 複数色LED
- ブザー
- 表示灯
- その他の簡易出力機器

特に入室可否問い合わせでは、回答結果を子機側へ返し、GPIO出力によって表示する構成を想定する。

例：

```text
OUTPUT_1 → 緑LED → 入室OK
OUTPUT_2 → 黄LED → 少し待って
OUTPUT_3 → 赤LED → 入室NG
```

初期段階ではデジタルON/OFF出力を基本とし、点滅、一定時間ON、PWM等は将来拡張として検討する。

### 4.5 GPIO設定例

```text
device_id = family-node-01
user_id   = father

GPIO 2  = INPUT_1
GPIO 3  = INPUT_2
GPIO 4  = INPUT_3

GPIO 10 = OUTPUT_1
GPIO 11 = OUTPUT_2
GPIO 12 = OUTPUT_3

INPUT_1  = BUSY
INPUT_2  = ENTRY_REQUEST
INPUT_3  = CALL

OUTPUT_1 = ENTRY_OK
OUTPUT_2 = ENTRY_LATER
OUTPUT_3 = ENTRY_NG
```

GPIO入力については、実装時に以下の設定項目を検討する。

- Active High / Active Low
- デバウンス時間
- 短押し／長押し判定の要否

MVPでは単純なデジタル入力とデバウンス処理を基本とする。

## 5. 子機初期設定

### 5.1 設定方式

子機設定にWeb UIは使用しない。

PC/MacとPico W/Pico 2 WをUSB接続し、USB CDC通信を利用して初期設定を行う方式を基本とする。

```text
PC / Mac
   │
   │ USB
   ▼
Pico W / Pico 2 W
   │
   └─ USB CDC設定モード
```

### 5.2 設定対象

想定する設定項目：

- Device ID
- 利用者ID
- 端末名称
- Wi-Fi接続情報
- 親機接続情報
- GPIO入力割り当て
- GPIO出力割り当て
- 各論理入力のイベント割り当て
- 各論理出力の機能割り当て

設定内容は子機の不揮発領域へ保存し、通常起動時に読み込む。

### 5.3 設定データ例

設定形式の詳細は今後決定するが、可読性とデバッグ容易性を考慮し、JSON等の利用を候補とする。

```json
{
  "device_id": "family-node-01",
  "user_id": "father",
  "buttons": {
    "1": "BUSY",
    "2": "ENTRY_REQUEST",
    "3": "CALL"
  }
}
```

## 6. 親機設計

### 6.1 基本機能

親機は以下を一元管理する。

1. 子機管理
2. 家族情報管理
3. イベント受信
4. イベント履歴管理
5. 現在状態管理
6. 問い合わせ／回答管理
7. 家族予定管理
8. Web UI提供
9. スマートフォン通知

### 6.2 子機通信

通信経路は原則として親機中心とする。

```text
子機 → 親機 → 子機
子機 → 親機 → Web UI
子機 → 親機 → スマートフォン通知
Web UI → 親機
```

子機同士の直接通信は基本設計に含めない。

通信プロトコルは未確定とし、MQTT、HTTP等から別途比較・決定する。

## 7. 情報モデル

家庭内情報は性質によって最低限以下に分類する。

### 7.1 Event

一時的に発生する出来事。

例：

- ご飯だよ
- ちょっと来て
- ポストへ投函された
- 入室問い合わせが発生した

概念データ：

```text
Event
  id
  timestamp
  source_device
  event_type
  actor
  target
  message
  priority
  notification_required
```

### 7.2 State

一定期間継続する現在状態。

例：

- 取り込み中
- 入室可能
- 外出中
- ポストに郵便物あり

概念データ：

```text
State
  owner
  state_type
  value
  started_at
  expires_at
```

### 7.3 Request / Response

家族間の簡単な問い合わせと回答。

代表例は入室可否問い合わせである。

```text
家族A子機
    │ ENTRY_REQUEST
    ▼
親機
    │
    ▼
家族B子機
    │ 通知
    │
    ├─ OK
    ├─ あとで
    └─ NG
    │
    ▼
親機
    │
    ▼
家族A子機
    │
    └─ LED等で回答表示
```

### 7.4 Schedule

家族の厳密なスケジュール管理ではなく、「今何をしている／これから何をするか」を大まかに共有するための予定情報とする。

例：

```text
父   09:00〜12:00  作業
母   14:00〜       外出
子   16:00〜       塾
```

本システムでは本格的なカレンダーサービスの代替を目的としない。

## 8. 入室可否機能

入室可否問い合わせは、専用端末ではなく家族ごとの子機を使用する。

### 8.1 基本シーケンス

```text
家族A子機
「入っていい？」ボタン
        │
        ▼
      親機
        │
        ▼
家族B子機
問い合わせ通知
        │
   ┌────┼────┐
   OK  あとで  NG
   └────┼────┘
        │
        ▼
      親機
        │
        ▼
家族A子機
回答結果表示
```

回答表示については、将来的にGPIO出力へLED等を接続して実現する。

## 9. ポスト投函チェッカー

ポスト投函確認機能は専用アーキテクチャを作らず、共通子機構成で対応する。

### 9.1 構成例

```text
Pico W / Pico 2 W
   │
   ├─ GPIO入力 → 投函検出センサー
   ├─ GPIO入力 → 確認／リセットボタン
   ├─ GPIO出力 → 郵便ありLED（任意）
   └─ Wi-Fi → 親機
```

### 9.2 状態遷移

投函検出時：

```text
MAIL_DETECTED
      ↓
mailbox_state = MAIL_PRESENT
```

郵便物回収時：

```text
確認ボタン押下
      ↓
MAIL_CLEARED
      ↓
mailbox_state = EMPTY
```

これによりWeb UIでは「イベント履歴」と「現在ポストに郵便物があるか」の双方を表示できる。

## 12. 代表的な利用例

### 12.1 ご飯だよ

```text
イベントボタン押下
      ↓
家族用子機
      ↓ Wi-Fi
親機
      ↓
イベント記録
      ↓
対象スマートフォンへ通知
```

### 12.2 取り込み中

```text
本人がボタン押下
      ↓
BUSYイベント
      ↓
親機が本人のStateを更新
      ↓
Web UIに「取り込み中」と表示
```

### 12.3 入室問い合わせ

家族Aの子機から問い合わせを送り、家族Bの子機のボタンで回答し、結果を家族Aの子機へ返す。

### 12.4 ポスト確認

センサーによる投函検出をイベントとして親機へ送り、親機が「郵便物あり」状態を保持する。郵便物回収後は子機の確認ボタンで状態を解除する。

## 15. 設計上の基本原則

本システムでは以下を設計原則とする。

1. **物理操作優先**  
   日常的なコミュニケーションはスマートフォン操作より物理ボタンを優先する。

2. **親機集中管理**  
   家庭内イベント・状態・予定の意味と管理は可能な限り親機へ集約する。

3. **子機共通化**  
   Pico W / Pico 2 W子機は共通ファームウェアを基本とする。

4. **GPIOと機能の分離**  
   物理GPIO番号とイベントの意味を直接固定せず、論理I/Oを介して関連付ける。

5. **拡張可能なI/O**  
   イベントボタンを必須としながら、センサー入力やLED等の出力を将来的に追加できる構成とする。

6. **Webは管理・閲覧中心**  
   Web UIは家庭内情報の閲覧、予定入力等に使用し、子機設定には使用しない。

7. **ゆるいコミュニケーション**  
   高機能なメッセージングシステムを目指さず、「声を掛けに行くほどではない」「メッセージを送るほどではない」家庭内の簡単な意思表示を容易にすることを目的とする。

---

## 16. 現時点のシステム定義

> **家庭内ゆるコミュニケーションツール**  
> Pico W / Pico 2 Wを使用したイベントボタン必須の汎用I/O子機と、Raspberry Pi Zero W / Zero 2 Wを使用した親機から構成される。家庭内の簡単なイベント、現在状態、問い合わせ、予定を親機へ集約し、物理ボタンとスマートフォンWeb UIを組み合わせて、家族間の負担の少ない情報共有を実現する。
