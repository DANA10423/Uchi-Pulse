# 親機 概要設計書

## 1. 目的

本書は、Uchi-Pulse 親機（Hub）の概要設計を定義する。

現段階では、親機プログラムの責務、起動時の基本動作、UDP受信からイベント保存までの流れ、および子機の通信状態・入室可否状態の管理について整理する。

Rustの具体的な構造体、スレッド構成、非同期ランタイム、データ型などの実装詳細は本書の対象外とする。

---

## 2. 親機の役割

親機は Raspberry Pi Zero W / Zero 2 W 上で動作し、家庭内ネットワーク上の子機を管理する。

主な役割は以下とする。

- 登録済み子機の管理
- 子機からのUDP通信受信
- HELLO / HEARTBEAT / EVENT の受信処理
- 子機の現在の通信状態管理
- 家族用子機の現在の入室可否状態管理
- EVENT受信履歴のSQLite保存
- EVENTに対するACK応答
- Web画面へのデバイス状態・入室可否・イベント情報提供
- 将来的な通知・表示処理への連携

---

## 3. 親機が管理する情報

親機が扱う情報は、永続情報と一時情報に分けて管理する。

### 3.1 永続情報

SQLiteに保存する。

- デバイスマスタ
- EVENT受信履歴

入室可否の現在値そのものを専用カラムとして保存しない。入室可否の変更はEVENT履歴として保存し、親機起動時の状態復元に利用する。

データベースの詳細は `docs/parent-database-design.md` を参照する。

### 3.2 一時情報

親機稼働中のメモリ上で管理する。

- 各子機の現在の通信状態
- 最終正常受信時刻
- 家族用子機の現在の入室可否状態

通信状態および入室可否の現在値そのものはSQLiteのデバイスマスタへ保存しない。

---

## 4. 親機起動時の基本処理

親機起動時は、登録済みデバイスを基準として状態管理を初期化する。

基本フローは以下とする。

```text
電源ON
  │
  ▼
親機初期化
  │
  ▼
SQLiteオープン／初期化
  │
  ▼
devices から有効な子機を取得
  │
  ▼
各子機の DeviceState を生成
  │
  ├─ 通信状態 = INITIAL_WAIT（未確認）
  ├─ last_seen_at = 未設定
  └─ 入室可否 = UNSET（未設定）
          │
          ▼
家族用子機について events から
最新の入室可否変更イベントを検索
          │
          ├─ 履歴あり → 最新値を復元
          └─ 履歴なし → UNSET のまま
  │
  ▼
UDP受信待受開始
  │
  ├── HELLO受信
  ├── HEARTBEAT受信
  └── EVENT受信
```

親機起動時に子機一覧を空から構築する方式は採用しない。

SQLiteの `devices` に登録され、かつ有効となっている子機を親機の管理対象とする。

通信状態は過去履歴から復元せず、必ず `INITIAL_WAIT` から開始する。一方、入室可否は利用者が明示的に変更した状態であるため、EVENT履歴から最新値を復元する。

---

## 5. DeviceState による状態管理

### 5.1 基本方針

子機の現在状態は親機のメモリ上で `DeviceState` として管理する。

概念上、最低限以下の情報を保持する。

| 項目 | 内容 |
|---|---|
| `device_id` | 子機ID |
| `last_seen_at` | 最後に正常なUDPメッセージを受信した日時。初期接続待ち中は未設定 |
| `status` | 通信状態。`INITIAL_WAIT` / `ONLINE` / `OFFLINE` |
| `room_access_status` | 入室可否。`UNSET` / `OK` / `NG` / `MEETING` |

`status` と `room_access_status` は独立した状態として扱う。

例えば、通信状態が `OFFLINE` であっても、最後に設定された入室可否が `MEETING` であれば、メモリ上ではその組み合わせを保持できる。

### 5.2 通信状態

管理する通信状態は以下の3種類とする。

| 状態 | Web表示例 | 意味 |
|---|---|---|
| `INITIAL_WAIT` | 未確認 | 親機起動後、その子機からまだ正常な通信を確認していない |
| `ONLINE` | オンライン | 正常な通信を確認済みで、現在通信可能と判断している |
| `OFFLINE` | オフライン | 一度通信を確認した後、一定時間正常な通信がない |

`INITIAL_WAIT` は「未登録」を意味しない。

DBには登録済みだが、現在起動している親機がまだ通信確認できていない状態を表す。

### 5.3 入室可否状態

家族用子機について、現在の入室可否を以下の4状態で管理する。

| 状態 | Web表示 | 意味 |
|---|---|---|
| `UNSET` | 未設定 | 入室可否が設定されていない |
| `OK` | OK | 入室してよい |
| `NG` | NG | 入室しないでほしい |
| `MEETING` | 会議中 | 会議・通話等のため入室を控えてほしい |

「在宅／外出」などの別状態は設けない。家庭内での利用上は通信状態を参照する。

また「取り込み中」等の追加状態は設けず、用途に応じて `NG` または `MEETING` で表現する。

### 5.4 起動時状態

親機起動時、`devices` から取得した有効な子機はすべて以下で初期化する。

- `status = INITIAL_WAIT`
- `last_seen_at = 未設定`
- `room_access_status = UNSET`

その後、家族用子機について `events` から最新の入室可否変更イベントを検索する。

- 最新履歴が存在する場合：そのイベント値を `room_access_status` に復元する。
- 履歴が存在しない場合：`UNSET` のままとする。

通信状態についてはEVENT履歴から復元しない。

### 5.5 正常受信時

通信仕様上有効な子機メッセージを受信した場合、対象子機を `ONLINE` とする。

対象となる基本メッセージは以下とする。

- `HELLO`
- `HEARTBEAT`
- `EVENT`

同時に、最後に正常な通信を受信した時刻を更新する。

入室可否変更を表すEVENTを受信した場合は、EVENT履歴へ保存した上で、対象子機の `room_access_status` も更新する。

### 5.6 オフライン判定

`ONLINE` の子機について、最後に正常な通信を受信してから設定されたオフライン判定時間を超えた場合、`OFFLINE` とする。

一度 `OFFLINE` となった子機でも、その後正常な通信を受信した場合は `ONLINE` へ復帰する。

通信状態が変化しても `room_access_status` は自動変更しない。

### 5.7 通信状態遷移

```text
親機起動
   │
   ▼
INITIAL_WAIT（未確認）
   │
   │ 正常なUDPメッセージ受信
   ▼
ONLINE（オンライン）
   │
   │ オフライン判定時間超過
   ▼
OFFLINE（オフライン）
   │
   │ 正常なUDPメッセージ受信
   └────────────────→ ONLINE
```

入室可否はこの通信状態遷移とは独立して変更される。

## 6. UDP受信時の基本処理

親機は子機からUDPパケットを受信し、JSONとして解析する。

正常なメッセージであることを確認した後、メッセージ種別に応じて処理する。

```text
UDP受信
  │
  ▼
JSON解析・妥当性確認
  │
  ▼
送信元子機を確認
  │
  ▼
メモリ上の通信状態を更新
  │
  ▼
メッセージ種別判定
  │
  ├── HELLO
  │     └─ 存在通知として処理
  │
  ├── HEARTBEAT
  │     └─ 生存通知として処理
  │
  └── EVENT
        ├─ イベント識別情報取得
        ├─ SQLiteへ保存
        ├─ 入室可否変更イベントの場合は
        │    room_access_status を更新
        └─ ACK送信
```

単にUDPパケットを受信しただけではONLINEとしない。

通信仕様上有効なメッセージとして正常に解析できた場合に、状態更新を行う。

---

## 7. EVENT受信処理

EVENT受信時は、イベント履歴をSQLiteへ保存する。

保存する基本項目は以下とする。

- 親機での受信日時
- `device_id`
- `event_id`
- UDPで受信したJSON本文

基本フローは以下とする。

```text
EVENT受信
  │
  ▼
device_id / event_id 取得
  │
  ▼
重複確認
  │
  ├── 未登録
  │      └─ eventsへ保存
  │
  └── 登録済み
         └─ 再登録しない
  │
  ▼
イベント内容を判定
  │
  └── 入室可否変更イベント
         └─ room_access_status 更新
  │
  ▼
ACK送信
```

UDP再送により同一EVENTを複数回受信しても、`device_id` と `event_id` の組み合わせによりイベント履歴を二重登録しない。

重複EVENTであってもACKは返す。

入室可否変更はイベントとして扱い、現在値専用のDB項目は設けない。イベントの具体的な識別方法やJSON項目は、イベント仕様の詳細設計で確定する。

---

## 8. HELLOとHEARTBEATの扱い

### 8.1 HELLO

HELLOは子機の起動・参加を示す存在通知として扱う。

HELLOだけをONLINE判定の必須条件にはしない。

HELLOに対するACKは行わない。

### 8.2 HEARTBEAT

HEARTBEATは子機の生存通知として扱う。

正常なHEARTBEATを受信した場合、対象子機をONLINEとして扱い、最終正常受信時刻を更新する。

HEARTBEATに対するACKは行わない。

---

## 9. 親機起動時のブロードキャスト

親機起動時に、子機へHELLO要求をブロードキャストする処理は必須としない。

親機はDB上の登録済み子機を `INITIAL_WAIT`（未確認）として表示し、各子機からのHELLO、HEARTBEAT、EVENTなどの自発的な通信を受信した時点でONLINEへ遷移させる。

これにより、親機起動時の問い合わせ用メッセージや全子機一斉応答などの追加仕様を避け、通信方式を簡潔に保つ。

---

## 10. Web表示との関係

親機のWeb画面では、SQLiteのデバイスマスタとメモリ上の `DeviceState` を組み合わせて表示する。

家族用子機については、通信状態に加えて入室可否も表示する。

例:

| デバイス | 通信状態 | 入室可否 |
|---|---|---|
| お父さん | オンライン | OK |
| お母さん | オンライン | 会議中 |
| 子ども | 未確認 | 未設定 |

設備用子機については、入室可否を表示対象としない。

これにより、親機再起動直後でも登録済みデバイスを一覧表示でき、入室可否については過去のEVENT履歴から最後に設定された状態を復元して表示できる。

通信確認前の登録済み子機を「登録なし」と誤って表示しないことを目的とする。

## 11. データベースとメモリの責務分離

親機では、以下の方針で情報を分離する。

```text
SQLite
  ├─ devices
  │    └─ 登録済み子機のマスタ情報
  │
  └─ events
       ├─ EVENT受信履歴
       └─ 入室可否変更の履歴
              │
              └── 親機起動時の状態復元に利用

メモリ
  └─ DeviceState
       ├─ 通信状態
       │    ├─ INITIAL_WAIT
       │    ├─ ONLINE
       │    └─ OFFLINE
       ├─ last_seen_at
       └─ 入室可否
            ├─ UNSET
            ├─ OK
            ├─ NG
            └─ MEETING
```

DBは「登録情報と過去に発生した事実」を保持する。

メモリは「現在利用する状態」を保持する。

通信状態は親機起動ごとに初期化するが、入室可否はEVENT履歴から最新値を復元する。
